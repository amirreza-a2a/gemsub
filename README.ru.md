# gemsub

[English](README.md) | [فارسی](README.fa.md) | [Русский](README.ru.md)

`gemsub` — это автоматизированный демон для проверки и публикации прокси-конфигураций и ссылок на подписки. Он принимает исходные ссылки из внешних источников, проверяет сетевую связность на транспортном уровне и доступность целевого сервиса с помощью активных проверок (проб), а затем раздает проверенные и классифицированные конфигурации через локальный HTTP-сервер подписок или Git-репозиторий. Программа предназначена для обнаружения региональных ограничений, выявления заблокированных или несовместимых маршрутов, отсеивания непригодных узлов для сервисов с верификацией целевой доступности (таких как Google Gemini), а также для формирования общей проекции сетевой доступности для стандартных прокси-клиентов.

---

## Ключевые возможности

- **Двухэтапное активное тестирование:** Сочетание проверок сетевого транспорта (TCP/TLS/uTLS) с реальной валидацией на прикладном уровне HTTP против целевых сервисов (включая Google Gemini).
- **Две канонические проекции:** Разделение пула конфигураций на строго проверенные для Gemini и общие работоспособные в сети узлы на основе единого авторитетного хранилища (Store).
- **Интерактивный терминальный интерфейс (TUI):** Разработан на базе Bubble Tea и Lip Gloss; включает динамическую таблицу узлов, автоматическое маскирование учетных данных (`[REDACTED]`), флаги стран, модальное окно деталей и просмотрщик логов на базе кольцевого буфера.
- **Фоновый режим без интерфейса (Headless):** Легковесная работа в фоновом режиме для серверов, сервисов systemd и ограниченных окружений без инициализации TUI.
- **Локальный HTTP-сервер подписок:** Раздача автоматически обновляемых подписок для клиентов Throne, Sing-box и Clash с фильтрацией по протоколам (`?proto=vless`), выбором формата (`base64` или `raw`) и эндпоинтом мониторинга здоровья.
- **Автоматическая публикация в Git:** Детерминированный экспорт, фиксация изменений и отправка проверенных конфигураций (`all.txt`, `vless.txt`, `vmess.txt`, `trojan.txt`, `meta.json`) в удаленный Git-репозиторий.
- **Персистентность и история:** Сохранение ограниченной истории циклов, счетчиков временных сбоев и рейтинга надежности между перезапусками в атомарных снапшотах, сжатых gzip.
- **Поддерживаемые протоколы:** VLESS, VMess, Trojan и Shadowsocks (`ss://`).

## Быстрый старт

Быстрый запуск в Linux одной командой:

```bash
# 1. Установка gemsub в ~/.local/bin
curl -sSfL https://raw.githubusercontent.com/amirreza-a2a/gemsub/main/scripts/install.sh | bash

# 2. Проверка установки и версии
gemsub --version

# 3. Создание минимального конфигурационного файла
cat <<'EOF' > config.json
{
  "sources": [
    "https://raw.githubusercontent.com/AvenCores/goida-vpn-configs/main/githubmirror/1.txt"
  ],
  "fetch_interval": "1h",
  "test": {
    "timeout": "10s",
    "gemini": {
      "block_phrases": [
        "isn't currently supported in your country",
        "not available in your country",
        "not available in your region"
      ]
    }
  },
  "serve": {
    "listen": "127.0.0.1:8765",
    "path": "/sub",
    "format": "base64"
  }
}
EOF

# 4. Запуск gemsub в интерактивном режиме TUI
gemsub -config config.json
```

После запуска `gemsub` сразу же начнет первый цикл тестирования и откроет доступ к подписке по адресу `http://127.0.0.1:8765/sub`.

## Установка

### Linux

#### Автоматический скрипт установки (рекомендуется)

Скрипт автоматически определяет архитектуру системы, скачивает нужный архив релиза, сверяет контрольную сумму SHA-256 с файлом `checksums.txt` и атомарно устанавливает бинарный файл в `~/.local/bin` без необходимости прав суперпользователя:

```bash
curl -sSfL https://raw.githubusercontent.com/amirreza-a2a/gemsub/main/scripts/install.sh | bash
```

Установка конкретной версии:

```bash
curl -sSfL https://raw.githubusercontent.com/amirreza-a2a/gemsub/main/scripts/install.sh | bash -s -- -v v0.1.0
```

Общесистемная установка в `/usr/local/bin` (требуются права root):

```bash
curl -sSfL https://raw.githubusercontent.com/amirreza-a2a/gemsub/main/scripts/install.sh | bash -s -- --system
```

#### Ручная установка из архива

1. Скачайте архив для вашей архитектуры со страницы GitHub Releases:
   - `x86_64` (`amd64`): `gemsub_Linux_x86_64.tar.gz`
   - `arm64` (`aarch64`): `gemsub_Linux_arm64.tar.gz`
   - `armv7` (`armhf`): `gemsub_Linux_armv7.tar.gz`
2. Скачайте `checksums.txt` и проверьте целостность файла:
   ```bash
   sha256sum --ignore-missing -c checksums.txt
   ```
3. Распакуйте архив и поместите исполняемый файл в каталог пользователя:
   ```bash
   tar -xzf gemsub_Linux_x86_64.tar.gz
   install -m 755 gemsub ~/.local/bin/gemsub
   ```

#### Пакеты для Linux (.deb / .rpm)

Системные пакеты устанавливают исполняемый файл в стандартный каталог `/usr/bin/gemsub`, а шаблон конфигурации — в `/etc/gemsub/config.example.json`.

Debian / Ubuntu:
```bash
sudo dpkg -i gemsub_<version>_linux_<arch>.deb
```

RHEL / Fedora:
```bash
sudo rpm -i gemsub_<version>_linux_<arch>.rpm
```

#### Поддерживаемые архитектуры Linux
- `x86_64` / `amd64` (64-битные процессоры Intel/AMD)
- `arm64` / `aarch64` (64-битные процессоры ARM)
- `armv7` (32-битные процессоры ARMv7)

#### Обновление
Повторный запуск скрипта установки скачивает и проверяет свежий релиз, обновляя бинарный файл без изменения существующих конфигураций и сохраненного состояния.

### Android / Termux

> [!NOTE]
> Данный пакет представляет собой **автономный исполняемый файл, совместимый с Termux**, и пока не является официальным пакетом в основном репозитории `termux-packages`. Проверка на физических устройствах находится в процессе; текущая валидация выполнена с помощью изолированных сборок и интеграционных тестов.

#### Поддерживаемая архитектура
- 64-битные устройства Android (`arm64` / `aarch64`), работающие под управлением Termux.

#### Автоматическая установка в Termux
Выполните скрипт установки непосредственно в терминале Termux:

```bash
curl -sSfL https://raw.githubusercontent.com/amirreza-a2a/gemsub/main/scripts/install-termux.sh | bash
```

Действия скрипта:
- Проверяет выполнение внутри пользовательского пространства Termux.
- Проверяет 64-битную архитектуру ARM (`aarch64`).
- Скачивает специальный архив `gemsub_Termux_arm64.tar.gz`.
- Сверяет контрольную сумму SHA-256 с `checksums.txt`.
- Устанавливает файл напрямую в `$PREFIX/bin/gemsub`.
- Не требует привилегий `root` или `sudo`.

#### Технические особенности и ограничения Termux
- **Формат бинарного файла:** Скомпилирован на чистом Go в виде позиционно-независимого исполняемого файла (PIE) ELF `DYN` с динамическим компоновщиком `/system/bin/linker64` и использованием системного DNS Android.
- **Работа с буфером обмена:** Копирование по клавише `y` в режиме TUI требует утилит пакета `termux-api` (`pkg install termux-api`) либо запуска демона в фоновом режиме (`-headless`).

### Фоновый режим (Headless)

Для серверов, сервисов systemd или фоновых сессий Termux:

```bash
gemsub -headless -config config.json
```

В фоновом режиме:
- Интерфейс TUI не инициализируется.
- Структурированные логи выводятся в поток ошибок (`stderr`).
- Процесс ожидает сигналы `SIGINT` или `SIGTERM`, завершая фоновые воркеры и сохраняя состояние перед выходом.

## Модель тестирования и валидации конфигураций

В `gemsub` реализован многоэтапный конвейер проверок, гарантирующий попадание в подписку только стабильных узлов:

```text
Источники → Извлечение ссылок → Нормализация и дедупликация
                                         ↓
                     Этап 1: Проверка сетевого транспорта
                       (TCP Connect, TLS / uTLS Handshake)
                                         ↓
                     Этап 2: Проверка целевого сервиса
                       (HTTP-запрос к целевому адресу)
                                         ↓
                     Анализ содержимого ответа и фильтрация
                                         ↓
                     Авторитетное хранилище (Store) и обновление
```

1. **Сбор и нормализация:** Загрузка ссылок, разбор параметров протоколов и приведение к каноническому виду для исключения повторных проверок.
2. **Проверка транспорта:** Тестирование сетевого слоя на ядре `sing-box` с реалистичными клиентскими фингерпринтами uTLS. При сбоях подключения TCP, ошибках рукопожатия или недоступности эндпоинта проверки узел помечается транспортной ошибкой (`conn_refused`, `timeout`, `tls_error`, `reality_error`).
3. **Валидация приложения:** Узлы с корректным транспортом переходят к тестированию реального HTTP-доступа к целевому сервису.
4. **Рейтинг надежности и история циклов:**
   - Каждый узел хранит ограниченный кольцевой буфер результатов последних проверок.
   - Кратковременные сетевые сбои отмечаются статусом `inconclusive`, и узлы с успешной историей остаются доступными в течение до `test.max_inconclusive_cycles` циклов.
   - Постоянные успешные прохождения повышают рейтинг надежности, определяющий позицию узла в списке подписки.

## Специфическая валидация для Gemini

Стандартные тесты прокси ограничиваются проверкой TCP-пинга или кодом 204 от серверов Google. Для Google Gemini этого недостаточно по следующим причинам:

1. **Региональные ограничения:** Прокси, расположенные в неподдерживаемых странах (или чьи IP-адреса неверно определяются в базах геопозиционирования), могут подключаться к сети Google, но получать страницы отказа в доступе.
2. **Неявная блокировка:** При региональных ограничениях или политиках доступа в некоторых окружениях сервисы Gemini могут возвращать ответы HTTP 200 или 403 со специфическим текстом отказа:
   - *"isn't currently supported in your country"*
   - *"not available in your country"*
   - *"not available in your region"*
3. **Блокировка нестандартного TLS:** В ряде сценариев инфраструктура Google может выявлять или ограничивать (throttle) рукопожатия TLS, исходящие не от стандартных браузеров.

`gemsub` решает эту задачу эмуляцией Client Hello реального браузера через uTLS, установлением полноценной HTTP-сессии с `https://gemini.google.com/` и поиском заданных фраз (`block_phrases`) в теле ответа. Узлы с региональными ограничениями изолируются с категорией ошибки `region_blocked`.

## Проекции: общая (Generic) и для Gemini

Хранилище `Store` формирует две независимые проекции:

```text
                    ┌─────────────────────────┐
                    │     Состояние Store     │
                    └────────────┬────────────┘
                                 │
                 ┌───────────────┴───────────────┐
                 ▼                               ▼
     Store.NetworkPassing()               Store.Passing()
    [Общая сетевая проекция]          [Проекция, проверенная для Gemini]
                 │                               │
                 ▼                               ▼
       /sub/generic или                /sub/gemini или
       /sub?projection=generic          /sub?projection=gemini
```

- **Общая проекция (`Store.NetworkPassing()`):** Содержит все узлы, успешно прошедшие базовую проверку транспорта (`https://www.gstatic.com/generate_204`), вне зависимости от блокировок со стороны Gemini. Подходит для общего веб-серфинга, мессенджеров и повседневных задач.
- **Проекция для Gemini (`Store.Passing()`):** Содержит только узлы, прошедшие как транспортную проверку, так и прикладную валидацию доступа к Gemini. Рекомендуется для работы с сервисами искусственного интеллекта.

## Публикация и работа сервера подписок

### Локальный HTTP-сервер подписок

Сервер отдает динамические подписки прокси-клиентам:

- **Основной эндпоинт:** `http://127.0.0.1:8765/sub` (по умолчанию отдает проекцию Gemini).
- **Выделенный общий эндпоинт:** `http://127.0.0.1:8765/sub/generic`
- **Выделенный эндпоинт для Gemini:** `http://127.0.0.1:8765/sub/gemini`
- **Эндпоинт метрик и здоровья:** `http://127.0.0.1:8765/healthz`

#### Параметры запроса (Query)

- `projection=generic` или `projection=gemini`: Выбор проекции на базовом эндпоинте `/sub`.
- `proto=vless`, `proto=vmess` или `proto=trojan`: Фильтрация по протоколу (синоним: `protocol=`).
- `format=raw` или `format=base64`: Переопределение кодирования ответа.

Примеры:
```bash
# Получение общей подписки в виде открытого текста
curl -s "http://127.0.0.1:8765/sub/generic?format=raw"

# Получение проверенных для Gemini узлов VLESS в кодировке Base64
curl -s "http://127.0.0.1:8765/sub/gemini?proto=vless&format=base64"

# Просмотр статистики и состояния сервера
curl -s "http://127.0.0.1:8765/healthz"
```

### Уровень публикации в Git (Git Publishing)

При значении `"publishing.enabled": true` программа в конце каждого цикла фиксирует изменения и отправляет обновленные файлы в Git:

- `all.txt`: Все пригодные ссылки (отсортированные по надежности и без дубликатов).
- `vless.txt`: Доступные ссылки протокола `vless://`.
- `vmess.txt`: Доступные ссылки протокола `vmess://`.
- `trojan.txt`: Доступные ссылки протокола `trojan://`.
- `meta.json`: Несекретные метаданные цикла (время, номер цикла, количество узлов).

Операция публикации атомарна: если за цикл состав и статус узлов не изменились, операция завершается без создания коммита.

## Сохранение состояния и персистентность

`gemsub` сохраняет состояние узлов между запусками с гарантией целостности:

- Данные записываются в файл `state_file` (по умолчанию `./gemsub_state.json`) и автоматически сжимаются в `./gemsub_state.json.gz`.
- Запись производится во временный файл с последующим атомарным переименованием, что исключает повреждение файла при аварийном отключении.
- При запуске `gemsub` восстанавливает сохраненное состояние узлов до возобновления регулярного тестирования, что позволяет HTTP-серверу подписок раздавать валидные восстановленные конфигурации, не дожидаясь завершения полного нового цикла проверок.

## Процесс релизов

Релизы запускаются публикацией Git-тегов и автоматизированы через GitHub Actions и GoReleaser:

1. **Создание тега:** Релиз инициируется отправкой тега семантического версионирования:
   ```bash
   git tag -a v0.1.0 -m "Release v0.1.0"
   git push origin v0.1.0
   ```
2. **Автоматический пайплайн (`.github/workflows/release.yml`):**
   - Задача `validate` выполняет `go vet` и `go test` с минимальными правами `contents: read`.
   - Задача `release` запускает GoReleaser v2 (`v2.18.1`) с правами `contents: write`.
   - GoReleaser выполняет кросс-компиляцию, формирует архивы, пакеты `.deb` и `.rpm`, генерирует файл контрольных сумм `checksums.txt`, внедряет метаданные версии и создает публикацию в GitHub Releases.
3. **Локальная проверка сборки релиза:**
   Разработчики могут проверить конфигурацию и выполнить тестовую сборку локально:
   ```bash
   # Проверка синтаксиса конфигурации GoReleaser
   make release-check

   # Сборка снапшота артефактов в каталог ./dist
   make release-snapshot
   ```

## Контрольные суммы и проверка целостности

Каждый выпуск сопровождается файлом `checksums.txt` с контрольными суммами SHA-256.

### Безопасность автоматических установщиков
Скрипты `scripts/install.sh` и `scripts/install-termux.sh` реализуют строгие проверки целостности:
- Точное совпадение имени файла (защита от подмены подстроками).
- Проверка уникальности записи (отклонение при дубликатах или отсутствии записи).
- Строгая проверка формата SHA-256 (64 шестнадцатеричных символа).
- Безопасное прерывание до распаковки (архив удаляется при несовпадении контрольной суммы).
- Поддержка стандартного бинарного маркера (`*<filename>`).

### Ручная проверка
```bash
sha256sum --ignore-missing -c checksums.txt
```

## Известные ограничения

- **Проверка в среде Termux:** Исполняемый файл для Termux проверен кросс-компиляцией, анализом заголовков ELF и тестами логики установки. Тестирование на реальных физических устройствах Android продолжается.
- **Архитектуры Termux:** Устройства с 32-битными процессорами ARM, x86 и x86_64 в Termux в настоящее время не поддерживаются.
- **Десктопные платформы:** Сборки для Windows и macOS в текущую матрицу релизов не включены.
- **Состояние гонки во внешней библиотеке:** В сетевом мониторе интерфейсов библиотеки `sing-box` (`route/network.go`) присутствует известное состояние гонки (data race) при высокой параллельной нагрузке с флагом `-race`. Оно изолировано в тестах и зафиксировано в реестре технического долга (`TD-008`).
